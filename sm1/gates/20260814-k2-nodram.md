# EXP 20260814-k2-nodram — K=2 是否仍然吃满喂料带宽

## 1. 目的

回答一个问题：**92.2 Gbit/s 这个数是 lane 算力堆出来的，还是喂料带宽卡出来的？**

`single-lane-59gbps-ok` 这个 tag 名字骗人——它构建出来的其实是 `P_NUM_LANES=4`
（fw=0x80110）。若吞吐真由喂料侧封顶，把 lane 砍一半应当**看不出差别**；
若由 lane 算力封顶，砍一半应当接近腰斩。这两种结局导向完全不同的下一步：
前者要去动协议时钟与 PAUSE 水位，后者要去动 `gen_mask` 的进位链。
在没分清之前，任何「提到 200 MHz」的工作都是在赌。

## 2. 假设与预测

**H1（喂料受限）**：K=2 ≈ 92 G，与 K=4 持平（±5%）。
**H0（算力受限）**：K=2 ≈ 46 G，约为 K=4 的一半。

同批次还要跑 K=1 作为第三点。三点连线才能定斜率——两点区分不了
「持平后突然掉」和「线性下降」。K=1 的预测值：H1 下 ≈ 62 G（单 lane 算力上限），
H0 下 ≈ 23 G。

## 3. 基线（含分辨力核对）

| 线速 | 286–296 Mbps | 同上 |
| bit 存档 | `.temp/bits/k4/` | 可随时烧回复测 |

基线**具备分辨力**（既非 0 也非饱和上限），符合 `13-v08mac-rgmii-timing.mdc` §3 的前置条件。

主机侧必须用**与固件同 tag 构建**的 CLI。HEAD CLI 会发 `data_tag=1` / `interleave=1`
且默认 8 KiB chunk，老固件的协议 FSM 直接锁死、板子失联——这一条已经踩过一次，
每次锁死都要重新 JTAG 烧写才能恢复。

## 5. 判据（跑之前定死）

- **H1 成立**：K=2 ∈ [87, 97] G 且 K=1 ∈ [59, 65] G → 供需模型可用，转入协议时钟 / PAUSE 水位方向。
- **H0 成立**：K=2 ∈ [44, 49] G → 算力受限，转入 `gen_mask` 进位链方向。
- **两者都不是**：模型推翻，停下来重算，**不硬推**。

每档跑 3 次，记 `wire_Mbps` 与 `dc_ms`，取中位数。单次不作数。

### 6.3 时序：未收敛，但违例全在 RGMII TX 引脚

`WNS = -0.326 ns`，**5 个失败端点，无一在解码域**：

| 端点 | slack |
|---|---|
| `PHYA_rgmii_txd[1]` | −0.326 |
| `PHYA_rgmii_txd[3]` | −0.285 |
| `PHYA_rgmii_txd[2]` | −0.228 |
| `PHYA_rgmii_tx_ctl` | −0.226 |
| `PHYA_rgmii_txd[0]` | −0.222 |

全部是 `OSERDESE3 → ODELAYE3 → OBUF` 的输出延时路径，逻辑级数 2。
`clk_out3`（125 MHz 解码域）**零违例**，`WHS = +0.017`（保持全过）。

与 K=4 基线对照，两类违例发生了**互换**：

| | K=4 基线 | K=2 本轮 |
|---|---|---|
| setup WNS | +0.140（0 违例） | **−0.326（5 违例，RGMII TX）** |
| WHS | −0.398（5 违例，RGMII RX 进 `ISERDESE3`） | **+0.017（0 违例）** |

两者都只动 RGMII I/O 侧，核心逻辑都干净。这与 `13-v08mac-rgmii-timing.mdc`
描述的 I/O 延时预算敏感性一致——但**方向反了**，需要板级判定，不能只看报告。

⚠ **这条会污染吞吐测量**：TX 侧坏帧的 FCS 已错，PC 网卡静默丢弃，
在 tshark 里根本不出现（规则 13 §1）。遥测应答走的正是 TX。
因此**上板后先过 ping 门禁（≥10 × `ping 5`，须 100%），再谈任何吞吐数**。
若 ping 掉档，说明 TX 违例是真的，`DELAY_VALUE` 调整须另开分支——那是第二个变量。

### 6.4 板级：ping 门禁与吞吐扫描

烧写 `AFTER_ILA_COUNT 0 / AFTER_VIO_COUNT 1`（known-good 签名），`fw=0x80110`。

**ping 门禁 50/50 = 100%**（10 × `ping 5`）。§6.3 的 RGMII TX setup 违例在板级**未显现**，
吞吐数据可信。

| 设置 | wire Mbps | dc_ms | blocks | 结果 | 吞吐 |
|---|---|---|---|---|---|
| unpaced（4 KiB chunk） | 316.25 | — | 0/2403 | **WEDGE**，ping 0/5 | — |
| `--target-mbps 150` | 147.3 | 1708.3 | 2403 | PASS | 47.2 G |
| `--target-mbps 200` | 183.9 | 1370.2 | 2403 | PASS | 58.8 G |
| `--target-mbps 250` | 233.9 | 1077.8 | 2403 | PASS | 74.8 G |
| `--target-mbps 290` | 252.6 | 998.1 | 2403 | PASS | 80.8 G |
| `--unpaced-gap-us 8` | 11.8 | 21254.9 | 2403 | PASS | 3.8 G |
| **`--target-mbps 320` ×3** | **288.2 / 287.9 / 286.2** | **877.0 / 878.1 / 882.1** | 2403 | **PASS** | **91.9 / 91.8 / 91.4** |

每次 PASS 后 ping 均 5/5。中位数：wire **287.9 Mbps**，dc **878.1 ms**，**91.8 Gbit/s**。

两个测量侧的坑，记下来免得重踩：

- `--target-mbps` 在本机**系统性欠达**（290 → 252.6，320 → 288.2）。要打到某个线速，
  目标值得往上开约 11%。判据要看 `wire_Mbps` 实测，不能看 target。
- `--unpaced-gap-us` 在 Windows 上**不是细调旋钮**：请求 8 µs，睡眠粒度把它放大成约 2 ms，
  速率从 316 掉到 11.8 Mbps（40× 过冲）。不要用它做速率微调。

## 7. 结论

**H1 成立，H0 被推翻。K=2 与 K=4 在同一喂料速率下吞吐完全一致。**

| | K=4 基线 | K=2 本轮 | 差 |
|---|---|---|---|
| wire Mbps（中位） | 285.9 | 287.9 | +0.7% |
| dc_ms（中位） | 883.8 | 878.1 | −0.6% |
| **吞吐** | **92.2 G** | **91.8 G** | **−0.4%** |

H0 预测 K=2 ≈ 46 G，实测 91.8 G，**差一倍**，不存在解释余地。
判据要求落 [87, 97]，实测 91.8，通过。

线性模型在本轮五个新点上继续成立（`G = 0.319 × wire_Mbps`，最大偏差 0.4%）。
连同基线三点，模型已在 150–288 Mbps 全区间、K=2 与 K=4 两种配置上得到验证。

**结论的作用范围**：证明了在 ≤ 288 Mbps 喂料下，**两条 lane 的算力就已经过剩**。
它没有证明单条 lane 够用——那是 K=1 那一档的事，也正是模型下一个可证伪点
（预测 ≈ 62 G，即 lane 算力首次成为限制项）。

### 7.1 一个未归因的观察：unpaced 会喂爆 K=2

unpaced（4 KiB chunk）冲到 316.25 Mbps 时板子彻底 wedge：`blocks_completed=0`、
ping 0/5、必须重新 JTAG 烧写。而 paced 288.2 Mbps 稳过三次。所以 K=2 的失稳阈值
落在 **288–316 Mbps** 之间。

**但这不能归到 K=2 头上。** K=4 基线从未被推过 296 Mbps，它自己的阈值是未知数。
两者可能一样。要判定必须在 K=4 上跑同样的 unpaced 与 320 档——那是独立的一次对照，
不属于本实验的变量，**另开分支**。

在此之前，任何「K=2 抗压更差」的说法都是没有对照的猜测。

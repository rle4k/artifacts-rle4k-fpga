# EXP 20260814-k1-burst-discriminator — K=1 的天花板是算力还是流控

## 1. 目的

`reports/2026-08-14-k1-k2-throughput-dataset.md` 测出 K=1 = 44.18 Gbit/s，
但那**不是饱和点，是崩溃阈值**：138.2 Mbps 下 3/3 通过且 `end_sync` 仅落后 6.2 ms
（与 50 Mbps 时相同），再快 3% 直接整板 wedge，没有过渡区。算力耗尽应当表现为
解码逐渐落后、`end_sync` 增长，而不是猝死。

且崩溃不是确定性的：K=2 在 234 Mbps 中途 wedge 过一次，而它在 293.5 Mbps 下 27/27 全过。
崩溃能发生在通过点之下 ⇒ 「K=1 天花板 = 138–143 Mbps」不是一个干净的容量测量。

论文里把 44.18 写成「单 lane 解码能力」会被要求解释崩溃机制。本实验用**不改 RTL、
不上 ILA** 的办法回答：这个阈值是 lane 的排空速率，还是缓冲水位／流控缺陷。

## 2. 假设与预测

判别原理：**算力受限的阈值只取决于平均速率；缓冲受限的阈值还取决于突发形状。**
lane 以固定速率排空，平均喂料超过它迟早溢出，与突发粒度无关；
而水位／流控缺陷下，同样的平均速率、更大的突发会更早顶穿队列。

- **H-COMPUTE**：崩溃阈值（按实测 `wire_Mbps` 计）在 4 KiB 与 1024 KiB 两种突发粒度下
  **一致**（差 ≤ 5%）。⇒ 44.18 G ≈ 单 lane 真实容量，缺陷只在于失效方式难看。
- **H-BUFFER**：两种粒度下阈值**显著不同**（差 > 15%），大突发阈值更低。
  ⇒ 44.18 G 是默认分块方式的产物，不是算力，论文不能把它当能力上限。

## 3. 基线

| 项 | 值 | 出处 |
|---|---|---|
| K=1 通过点 | 137.96 Mbps（3/3），44.18 G | 数据集报告 |
| K=1 崩溃 | 142.7 Mbps（0/1）、147.5 Mbps（0/6） | 同上 |
| K=2 通过 | 至 293.45 Mbps（27/27），93.60 G | 同上 |
| 默认分块 | paced→1024 KiB，≥200 Mbps→256，unpaced→4 | CLI `--help` |

K=1 基线**具备分辨力**：138 通过、143 崩溃，区间只有 3%，足够分辨阈值位移。

## 4. 唯一变更

**不改任何设计文件。**唯一变量是主机发送的突发粒度 `--sendqueue-chunk-kib`，
平均速率由 `--target-mbps` 控制并以实测 `wire_Mbps` 为准。

## 5. 判据（跑之前定死）

分别在 `--sendqueue-chunk-kib 4` 与 `1024` 两种粒度下，用二分法定出 K=1 的崩溃阈值
（判定精度 ±3 Mbps 实测线速）：

- **H-COMPUTE 成立**：两阈值相差 ≤ 5% → 44.18 G 可作为单 lane 容量写入论文，
  另附失效方式的说明。
- **H-BUFFER 成立**：两阈值相差 > 15%，且大突发的更低 → 44.18 G 只能作为
  「默认配置下的可持续吞吐」，不得表述为 lane 算力上限。
- **落在 5%–15% 之间**：不足以定性，如实记录，不硬下结论。

必须成立的控制条件，否则不是对照实验：

- 两种粒度下**实测 `wire_Mbps` 必须可比**。`--target-mbps` 在本机欠达约 11%，
  且欠达幅度可能随 chunk 变化 —— 要按实测线速对齐，不能按 target 对齐。
- 每个判定点 3 次；通过点须 3/3，崩溃点须至少 2 次复现，避免把随机 wedge 当阈值。
- 每次烧写后先跑一次**丢弃的预热运行**（两种粒度同等对待）：已知烧写后第一次
  大流量突发会 wedge，且该现象与 lane 数无关。
- 每次运行后 `ping 5` 须 5/5；上板前 10 × `ping 5` 门禁须 100%。

### 6.2 主机侧标定：`--target-mbps` 的欠达强烈依赖 chunk（本实验最大的方法学障碍）

同一 `--target-mbps 140`、同一数据集，仅改 chunk（全量 2403 block 单轮）：

| chunk (KiB) | 实测 wire_Mbps | 达成率 | wall_ms | es_ms |
|---|---|---|---|---|
| 4 | 7.797 | 5.6% | 32173.0 | 25.9 |
| 16 | 71.790 | 51.3% | 3494.2 | 19.6 |
| 64 | 85.525 | 61.1% | 2933.1 | 31.2 |
| 256 | 130.526 | 93.2% | 1921.8 | 4.8 |
| 1024 | 137.90–138.16 | 98.5% | 1815.7–1819.0 | 4.6–7.3 |

原因在发送路径而非板卡：`main_cli_v8.cpp` 的 `BatchSender` 把整个 sendqueue 交给
`pcap_sendqueue_transmit(..., sync=1)`，由驱动按每帧时间戳释放。chunk = 1024 KiB 时一个队列约
700 帧、跨度约 60 ms，驱动能把流量**抹平**成目标速率；chunk = 4 KiB 时一个队列只装得下约 2 帧
（`4096 / (1500 + sizeof(pcap_pkthdr))`），队列内跨度仅几十微秒，于是实际波形变成
「2 帧线速微突发 + 驱动开销造成的毫秒级空档」，平均速率被开销钉死。

**这一点直接推翻了 charter §2 里「chunk 越大 = 突发越大」的隐含前提**（见 §7.3）。

更麻烦的是 4 KiB 下 target→线速**既非线性也非确定**：

| chunk 4 KiB, target | 实测 wire_Mbps |
|---|---|
| 100 / 140 | 7.071 / 7.797 |
| 200 | 19.873 / 20.024 / 20.495 / 20.537 / 21.831 / 27.518（6 次预热轮） |
| 210 … 218 | 24.15 / 27.04 / 24.25 / 30.06 / 34.96 / 39.53 / 30.09 / 35.61 / 43.42 / 41.63 / 55.92 |
| 219 | **108.006 / 90.370 / 79.151**（同一 target 三次） |
| 220 | 122.343 / 118.667 |
| 221.5 / 222 | 163.925 / 173.665 |
| 1000 | 322.791 |

同一 target 219 三次分别落在 79.2 / 90.4 / 108.0 Mbps。因此 4 KiB 一侧**只能按实测线速散点定界**，
不能按 target 定界 —— 这正是 charter §5 控制条件「按实测线速对齐」所要求的做法，但也意味着
4 KiB 一侧的判定精度天然差于 1024 KiB 一侧。

### 6.5 `end_sync_ms` 行为：两侧都**没有**逼近悬崖时的增长

这是判别算力饱和的直接观测量，两条 arm 都要看：

| arm | 低速区 es_ms | 最后一个通过点 es_ms | 崩溃点 es_ms |
|---|---|---|---|
| 1024 KiB | 5.8–6.3（99 Mbps） | **5.6 / 6.2 / 6.3**（140.0 Mbps） | 8007.4 / 8040.1（超时值） |
| 4 KiB | 5.4–60.3（20–40 Mbps） | 8.4 / 6.4 / 18.2（79–108 Mbps） | 8022.3–8069.0（超时值） |

- **1024 KiB 一侧：es 完全没有增长趋势。** 从 49.7 Mbps（历史数据 6.3 ms）到 140.094 Mbps（6.2 ms），
  线速涨了 2.8 倍，es 纹丝不动，占 `dc_ms` 的 0.35%。下一档 141.655 Mbps 直接整轮归零。
  **「6 ms 滞后 → 再快 1.1% 就猝死」，过渡区宽度为零。**
- **4 KiB 一侧：es 偏大且抖动（5.4–133.6 ms），但与线速不相关**（133.6 ms 出现在 24.153 Mbps，
  而 108.006 Mbps 时只有 8.4 ms）。这是小 chunk 波形本身造成的间歇性积压，不是随速率单调增长的饱和特征。
- 崩溃轮的 `es ≈ 8000 ms` 是等待超时常量，不是滞后测量值，**不可**当作「滞后增长」的证据。

**结论：两种粒度下都没有观测到解码滞后随喂料速率增长。** 按 charter §1 的判据，
这与「算力耗尽」的预期表现不符 —— 算力耗尽应当先看到 es 增长，再看到失败。

### 6.7 补充观测（非判定点，供后续排查）

- **单轮 target=140、仅改 chunk** 的全量轮（§6.2 表）在 4/16/64/256/1024 KiB 下**全部通过**，
  说明该表只反映主机达成速率，不含板卡阈值信息。
- **300 block 短轮标定**（`*_cal.txt`，`--max-blocks 300`）：chunk 1024 / target 140 得 137.997–138.244 Mbps，
  与全量轮的 137.903–138.158 一致（差 < 0.25%），故短轮可用于**速率标定**；
  但短轮的**通过/崩溃判定不可外推到全量轮**（例：4 KiB 短轮在 119.066 Mbps 通过，
  而全量轮在 118.667 Mbps 崩溃），所有判定点因此一律用全量 2403 block。
- **wedge 后板卡有时无需重烧即自行恢复**：本轮多次观察到 `ping 0/5` 之后，下一条 `verify` 命令
  又能 `blocks_completed=300` 且 `ping 5/5`。这与数据集报告 §3.3「须 JTAG 重烧才能恢复」的记述**不符**，
  是一个新观测。本实验**未**依赖该自恢复：所有判定点前都执行了真实重烧 + 门禁 + 预热。
- 256 KiB 的 300 block 短轮在 147.633 与 159.376 Mbps 通过、184.099 Mbps 崩溃 —— 即
  256 KiB 的阈值**高于** 1024 KiB 的 140.87。若属实，阈值对 chunk **非单调**（在 256 KiB 附近有极大值）。
  这只是短轮证据，**未**用全量轮验证，不参与本实验判定，仅记录以免后人误以为「chunk 越大越好」。

## 7. 结论

### 7.1 两个阈值（按实测 wire_Mbps）

| arm | 最高 3/3 通过 | 最低 2/2 复现崩溃 | 阈值 | 精度 | 对应解码吞吐 |
|---|---|---|---|---|---|
| **1024 KiB** | 140.094 Mbps | 141.655 Mbps | **140.87 Mbps** | ±0.78 | 45.27 Gbit/s |
| **4 KiB** | 108.006 Mbps | 118.667 Mbps | **113.34 Mbps** | ±5.33 | 36.43 Gbit/s |

（解码吞吐按数据集 §1.3 的恒等式 `G = 0.32137 × wire_Mbps` 换算，仅在 `es ≈ 0` 时成立。）

差值 = 27.53 Mbps = **19.5%**（以 1024 KiB 阈值为分母）。

两侧取界的极端组合也都超过 15%：

- 最保守（4 KiB 取上界 118.667，1024 KiB 取下界 140.094）：差 21.43 Mbps = **15.29%**
- 最激进（4 KiB 取下界 108.006，1024 KiB 取上界 141.655）：差 33.65 Mbps = **23.75%**

即：**无论怎样在各自的不确定区间里取值，两个阈值的差都 > 15%。**

### 7.2 对照 charter §5 判据

| 判据 | 阈值 | 实测 | 是否成立 |
|---|---|---|---|
| H-COMPUTE：两阈值差 ≤ 5% | ≤ 5% | **15.3%–23.8%** | **否证** |
| H-BUFFER 幅度条款：差 > 15% | > 15% | 最保守 15.29% | **成立** |
| H-BUFFER 方向条款：大突发更早崩溃 | — | 见 §7.3 | **需按实际波形重述** |
| 落在 5%–15%（不足以定性） | — | 最保守值 15.29% 已越线 | 否 |

**判定：H-BUFFER 成立，H-COMPUTE 否证。**

判别原理（charter §2）说得很清楚：**算力受限的阈值只取决于平均速率。**
实测的两个阈值都是**按实测平均线速**定出来的，却相差 19.5% —— 同一块板、同一 bit、同一数据集、
同一解码时钟，只改主机的发送分块方式，板卡能吃下的**平均**速率就变了近两成。
所以 138–142 Mbps 这个天花板**不是**单 lane 的排空速率。§6.5 的 `end_sync_ms` 证据独立指向同一结论：
两种粒度下解码都从未落后，崩溃前没有任何饱和迹象。

### 7.3 方向条款为何要重述（必须写明，否则是把判据往数据上掰）

charter §2 写「大突发阈值更低」，其隐含前提是 **chunk 越大 = 突发越大**。
§6.2 证明**这个前提是错的**：`pcap_sendqueue_transmit(sync=1)` 让驱动按时间戳逐帧释放，
1024 KiB 的队列装约 700 帧、跨度 60 ms，出来的是**被抹平的平滑流**；
4 KiB 的队列只装约 2 帧，出来的是**线速微突发 + 毫秒级空档**。
按 chunk 数值读，「大 chunk」反而更晚崩溃（140.87 > 113.34），方向与 charter 字面相反；
按**实际线上波形**读，更突发的那一侧（4 KiB）更早崩溃，方向与 H-BUFFER 的物理预期一致。

因此本文的写法是：**幅度条款（>15%）按字面成立，方向条款按字面不成立、按物理成立。**
两种读法都不改变核心结论 —— 阈值依赖突发形状，不是纯算力。

### 7.4 机理候选（未验证，不写进论文的因果句）

`07-v08mac-cli.mdc` 记录过：`mac_proto` 存储转发在全速下 RX 丢 3515 帧（17.0%）而 **FCS 错误为 0**，
即 RX 侧存在缓冲溢出而非物理层误码。4 KiB 的线速微突发正好是那条路径最不利的输入形状。
K=2 交叉核对（§6.6）显示该阈值随 lane 数上移 2.42×，说明溢出点在**每 lane 的接收/输入缓冲**，
而不是共享的主机侧或 TEMAC 侧。

**但这仍只是候选。** 定性需要 ILA 抓 FIFO 水位与 PAUSE，本轮按 charter「不改 RTL、不上 ILA」的
约束**没有做**。此处到「阈值随突发形状变化、且随 lane 数缩放」为止。

### 7.5 对论文的直接后果

**44.18 Gbit/s 不能写成「单 lane 解码能力 / lane 容量」。**
它是「默认发送配置（paced，sendqueue chunk = 1024 KiB）下测得的可持续吞吐」。
同一块板同一 bit，换成 4 KiB 分块，可持续吞吐就降到 36.43 Gbit/s（−19.5%）；
而两种配置下解码都从未落后（`es` 5–8 ms），说明真实的 lane 算力上界**两次都没被摸到**。

可写的表述：**单 lane 在默认发送配置下的可持续解码吞吐 = 44.18 Gbit/s，
其上限由主机发送突发形状触发的板级流控/缓冲缺陷决定，而非解码算力；单 lane 算力上界本轮未测到。**

### 7.6 本实验自身的局限

1. **4 KiB 一侧精度 ±5.3 Mbps，未达 charter 要求的 ±3 Mbps**（§6.4），因主机 target→线速在该
   粒度下随机（同 target 三次 79.2/90.4/108.0）。结论不受影响，因为最保守取界仍 > 15%。
2. **每个判定点 3 次，样本量小。** 1024 KiB 一侧散布极小（0.06%），4 KiB 一侧散布极大（同 target 26%）。
3. **只测了两个粒度的阈值。** 16/64/256 KiB 只有短轮标定数据，不足以画出阈值—chunk 曲线；
   §6.7 的 256 KiB 短轮提示该曲线可能非单调，未验证。
4. **崩溃机理未定**（§7.4），本轮按约束未上 ILA。
5. **仍未做内容正确性校验**：全部 `--parallel`（send-only，CRC gate off），判据是
   `blocks_completed == 2403` 与 `ping 5/5`，不回答「解码结果对不对」。
6. **时序未收敛**（WNS = −0.326 ns，5 个 RGMII TX 端点）这一既有条件在两条 arm 中相同，
   不构成 arm 之间的混淆因子，但绝对数值仍依赖本机这颗器件与当前温度。

# E8 — 发送端批量化 + 接收侧突发容限

前置：`reports/2026-08-09-e7-block-pacing.md`（按块节流，最优点 580 µs / 200 Mbit/s，
FPGA 通路 1.668 s / 48.3 Gbit/s）。E7 把与架构极限的 22% 差距归因于两处非解码器瓶颈：
PC 只能发 279 Mbit/s、接收侧吃不下单块突发。E8 把这两处都拆掉了。

**结论先说：两处瓶颈真实存在且都已消除，但端到端只快了 2%（1.668 s → 1.636 s）。
E7 的归因是错的**——它们是「更靠后才会碰到的天花板」，不是当时的约束项。当前的约束项
是解码器自己：每块有约 620 µs 的时间下限（理论下限 524 µs，效率 85%），外加约
300 Mbit/s 的压缩侧消化速率。

---

## 1. 发送端

### 1.1 先量分摊：每帧堆分配不是成本

`--dry-run` 只走构帧路径、不碰网卡；真实发送多的那部分就是 `pcap_sendpacket`。

| 路径 | 20639 帧总耗时 | 每帧 |
|---|---|---|
| 构帧（含每帧一次 `std::vector` 分配 + memcpy） | 2.5 ms | **0.12 µs** |
| 构帧 + `pcap_sendpacket` | 892 ms | 43.2 µs |

每帧堆分配占整条发送路径的 **0.3%**。E7 报告里把它列为待优化项是量级判断错误；
真正的成本是每帧一次用户态/内核态往返。预分配缓冲照样做了（`build_frame()` 写入
调用方给的缓冲，`raw_send()` 用一个静态帧缓冲），但**不是**加速的来源。

### 1.2 批量发送

`pcap_sendqueue_alloc` / `pcap_sendqueue_queue` / `pcap_sendqueue_transmit`。
一次 `transmit` 把整批交给驱动；批大小 8 MB，**只在块边界 flush**，且在块边界预留
一整块的余量（`kMaxBlockWireBytes` = 128 KB）而不是一帧的余量——下一次能 flush 的
机会在一整块之后。整条 strip 分 4 批。

flush 是时间表上的一个洞，放在块之间只会推迟下一块的起点，是安全方向。

| 模式 | 线上速率 | 每帧 |
|---|---|---|
| 每帧一次 `pcap_sendpacket`（`--no-sendqueue`） | 278.5 / 278.3 Mbit/s | 43.2 µs |
| 批量 `pcap_sendqueue`（默认） | **953.2 / 953.4 / 952.0 Mbit/s** | 12.7 µs |

**3.42×**。953 Mbit/s 是本表口径（不含前导码/FCS/IFG）；折算到链路占用是
1511 B 帧 + 24 B 开销 → **968 Mbit/s，已是千兆线速**。发送端不再是限制项。

### 1.3 定速交给驱动，`pace_slips` 结构性消失

`transmit(sync=1)` 按每帧 `pcap_pkthdr.ts` 释放。所以节流不再是「用户线程自己
spin 等待」，而是驱动按时间戳发——Windows 调度抖动这一项从模型里整个消失了。
CLI 侧改为**预先算出**释放时刻（`SendSchedule`），不再实时等待：

- 块门控：`block_open = max(上一块 block_open + T, 上一块结束时刻)`（相对上一块的
  实际开启，不是累计时间表——块超时是常态，不能当欠账攒着补发）
- 块内：`cursor = block_open + 已释放位数 / cap`

实测精度（2403 块，理想 = 2403 × T）：

| T | 理想 | 实测 | 误差 |
|---|---|---|---|
| 540 µs | 1297.6 ms | 1305.7 ms | +0.63% |
| 560 µs | 1345.7 ms | 1354.3 ms | +0.64% |
| 600 µs | 1441.8 ms | 1449.5 ms | +0.53% |
| 1000 µs | 2403.0 ms | 2409.0 ms | +0.25% |

恒速模式同样准（设 400 → 实测 395.1 Mbit/s）。残余误差就是那 4 次 flush 的空档。
`pace_slips` 现在恒为 0，不是「改善了」而是**这个量已经没有对应的物理过程**。

`--no-sendqueue` 保留旧路径，E4/E7 的测量仍可复现。

## 2. 接收侧突发容限

### 2.1 加在哪一级，为什么

RX 链（`src/master_wrapper_v8.v`）：

```
TEMAC(8b) → axis_dwidth_converter_1(8→64) → axis_data_fifo_1(CDC) → axis_data_fifo_0(packet) → mac_proto
```

`rx_axis_dwidth_converter0.s_axis_tready` 在 `master_wrapper_v8.v:377` 是**空连接**——
MAC 从来不被背压，转换器吃不下的帧直接掉在地上，而且丢帧点恰好就是
`dbg_rx_mac_frames − dbg_rx_dwc_frames` 这个计数差。所以要加深的是**转换器下游最近
的一级**，即 CDC FIFO `axis_data_fifo_1`；顺带把它后面的 packet FIFO
`axis_data_fifo_0` 一起加深（同一 IP 配置也被 TX 用，多花的 BRAM 无所谓）。

### 2.2 加到多深（先算）

| 量 | 值 |
|---|---|
| 最大块 payload | 52,840 B |
| 帧数 | ⌈52840/1492⌉ = 36 |
| 线上字节 | 52,840 + 36×19 = **53,524 B** |
| 折 64 bit AXI 字 | 6,691 |
| 原深度 | 2048 字 = 16 KB → **不到一整块的三分之一** |
| 新深度 | **8192 字 = 64 KB**，装下最大块还余 18% |
| RX 两级合计 | 128 KB ≈ 2.4 个最大块 |

发送端修好之后 PC 真的能以线速把一整块打过来，所以「装不下一整块」这件事从纸面
风险变成了实测丢帧。

### 2.3 代价与时序

| 项 | PROD 基线 | E8 |
|---|---|---|
| Block RAM Tile | 18.5 / 600 (3.1%) | **66.5 / 600 (11.08%)** |
| RAMB36 | — | 64 |
| CLB LUT | — | 40,594 (16.75%) |
| WNS / TNS / 失败端点 | −0.326 / −1.287 / 5 | **−0.326 / −1.287 / 5** |
| WHS | +0.028 | **+0.031** |

+48 tile，每个 FIFO 实例 16 个（8192 × 74 bit = 606 Kb）。时序**逐位相同**：
同样是那 5 个已知的 `PHYA_rgmii_rxd[3:0]`/`rx_ctl` 端点（`13-v08mac-rgmii-timing.mdc`
已判定与功能缺陷无因果）。

### 2.4 效果

**完全不加块内限速、块内按线速突发**：

| 块周期 | 丢帧（2 次） |
|---|---|
| 540 µs | 1913 / 1980 |
| 600 µs | 234 / 217 |
| 700 µs | 32 / 32 |
| 850 µs | 0 / 9 / 2 |
| **900 µs** | **0 / 0 / 0** |
| 1000 µs | 0 / 0 |
| 2000 µs | 0 / 0 |

T ≥ 900 µs 时线速突发零丢帧——加深之前这是做不到的。**单块突发已经吃得下。**

## 3. 新的最优工作点：块内限速仍然需要

单纯靠突发容限要 900 µs/块（2170 ms），比 E7 还慢。原因是每块解码时间不是常数：
块越大解码越久，纯块门控只能按最差块定周期。加上块内限速等于给大块额外的时间。

二维扫描（`send` + VIO 计数，每格 2–4 次；括号内为各次丢帧数）：

| T \ cap | 200 | 250 | 300 | 400 | 无 |
|---|---|---|---|---|---|
| 540 | 88/94/84 | — | — | 1706/1749 | 1913/1980 |
| 580 | 13/4/0 | — | 573/585 | — | — |
| 600 | 0/0/0/31 | 15/0/0 | — | — | 234/217 |
| 620 | 0/0/0/9 | 16/0/31 | **0/0/0** | — | — |
| 640 | — | **0/0/0/0/0/0** | **0/0/0** | — | — |
| 660 | — | — | 0/77 | 0/30/0 | — |
| 700 | — | — | — | 0/5/1/0 | 32/32 |
| 720 | — | — | — | **0/0/0/0** | — |
| 900 | — | — | — | — | **0/0/0** |

恒速模式（无块门控）在 150 Mbit/s 就开始丢（57/63/58），170 丢 321–355 ——
E4/E7 的结论仍然成立：**必须按块节流**。

**选定工作点 620 µs / 300 Mbit/s**，整 strip `verify` 3/3 逐位通过，FPGA 通路 1636 ms。
边界很陡：**600 µs / 300 Mbit/s 直接失败**，而且失败形态是解码器停住（`fpga_path_ms`
跑到 548 s 的轮询上限、`fpga_words=0`）——丢帧不是「少一点数据」，是整条 strip 报废。

## 5. 三口径与差距归因

| 指标 | E7 (580/200) | E8 (620/300) |
|---|---|---|
| 压缩侧传输率 | 149.6 Mbit/s | 163.0 Mbit/s |
| 解码后吞吐 | 48.3 Gbit/s | 49.3 Gbit/s |
| 2403 块 FPGA 通路墙钟 | 1.668 s | **1.636 s** |
| PC 参考解码墙钟（另计） | ~20 s | 20.6 s |

距 2403 × 540 µs ≈ 1.30 s / 62.1 Gbit/s 还差 **26%**。差在哪：

1. **每块时间下限约 620 µs，不是 540 µs。** 4 MiB / 65536 字 @125 MHz = 524 µs 是硬底，
   实测下限 620 µs ⇒ 效率 **85%**，不是 E7 假设的 97.1%。2403 × 620 µs = 1490 ms，
   已经占掉 1636 ms 里的 91%。
2. **压缩侧消化速率约 300 Mbit/s。** 72 个大块被 cap 而不是被周期约束（`blocks_late=72`），
   多花约 40 ms。
3. 余下约 105 ms 是 `fpga_wait_ms`（最后一块解码 + CRC 查询往返）。

**发送端与接收缓冲都已不在关键路径上**：PC 能发 968 Mbit/s（工作点只用 163），
RX 能吞下线速单块突发（工作点根本不打到线速）。要再往 62 Gbit/s 走，只能动解码器
本身——多实例并行（V1023 方案 e）、位宽或时钟——这三项按边界仍待用户拍板。

# E7 —— 按块自适应节流

数据：`D:\outputs\rle4k_1`（2403 块，压缩 30,792,856 B / 线上 31,184,997 B，解码后 157,450,624 字 = 80.615 Gbit）。
位流：`reports/bitstreams/2026-08-09-streamend-drainfix-PROD-noila`（量产、无 ILA）。
判据：VIO 的 `dbg_rx_mac_frames − dbg_rx_dwc_frames`，即位宽转换器入口被背压丢掉的帧。

## 1. 结论

**光有块周期不够，还必须限制块内速率。** 两个约束同时成立，最优点在二维前沿上：

| | 干净点 | 2403 块发送墙钟 | 线上 Mbit/s | 解码后 Gbit/s |
|---|---|---|---|---|
| E4 恒速基线 | `--target-mbps 138` | 1.934 s | 136.5 | 41.7 |
| 只按块周期（块内打线速） | 650 µs | 1.590 s | 156.9 | 50.7 |
| **按块周期 + 块内限速** | **580 µs / 200 Mbit/s** | **1.520 s** | **164.1** | **53.0** |

全量验收在 580 µs / 200 Mbit/s 下通过，**FPGA 通路 1.668 s，解码后 48.3 Gbit/s**
（比 E4 的 1.960 s / 41.1 Gbit/s 快 **17.5%**）。

预测的 1.30 s / 62 Gbit/s **没有达到**，差的两截都定量归因了，见 §5。

### 起跳点 600–650 µs 不能直接读成「每块 625 µs」

理论硬底 524 µs、E4 反推的实际解码时间 540 µs，**都比这个起跳点小**。
差额不是解码器变慢了，而是这一档的块内是**突发**：起跳点被块内突发顶高了。
把块内速率限住之后（§3），580 µs 就干净了 —— 更靠近 540 µs。
所以「起跳点」只有在同时说明块内速率时才有意义，**单看块周期会把解码时间高估约 20%**。

## 3. 块内突发确实打穿缓冲

同一个 560 µs 块周期，只改块内速率：

| 块内速率 | 560 µs 下的丢帧 |
|---|---|
| 不限（PC 最快 279 Mbit/s） | 435, 452, 477 |
| 220 Mbit/s | 66, 45, 62 |
| 200 Mbit/s | 17, 0, 7 |
| 190 Mbit/s | 3, 3, 5 |
| 180 Mbit/s | **0, 0, 0** |
| 160 Mbit/s | **0, 0, 0** |

丢帧随块内速率单调下降而块周期没变 —— **突发是独立于平均速率的第二个约束**，这条实测坐实。

### 3.1 二维扫描

|---|---|---|---|---|---|---|

| 650 µs | — | — | — | — | — | **0, 0, 0** |

干净点的发送墙钟：

| 配置 | 发送墙钟 s | 线上 Mbit/s | 解码后 Gbit/s |
|---|---|---|---|
| 160 / 540 µs | 1.624 | 153.7 | 49.7 |
| 180 / 560 µs | 1.538 | 162.2 | 52.4 |
| **190 / 570 µs** | **1.522** | **163.9** | **53.0** |
| **200 / 580 µs** | **1.520** | **164.1** | **53.0** |
| 200 / 600 µs | 1.561 | 159.8 | 51.6 |
| 不限 / 650 µs | 1.590 | 156.9 | 50.7 |

前沿很平：190/570 与 200/580 只差 2 ms。选 **200 / 580** 做验收，因为它离丢帧区更远一格
（200 Mbit/s 在 560 µs 就已经开始零星丢，570→580 是往里走了一步；190 在 560 µs 就丢 3–5 帧）。

### 3.2 缓冲的两个不同数字

用「峰值积压 ≈ C·T_dec/4」（块内以速率 C 到达、解码在 T_dec=540 µs 内均匀消耗，
最坏块长 C·T_dec/2）反推突发容限：

```text
C = 200 Mbit/s = 25.0 MB/s  ->  3.4 KB   (干净)
C = 279 Mbit/s = 34.9 MB/s  ->  4.7 KB   (丢帧)
```

即**突发容限只有 3.5–4.5 KB**，远小于 E4 从持续赤字反推的 13–23 KB。
两个数字量的不是同一件事：13–23 KB 是整条链在**持续**入不敷出时的总余量，
3.5–4.5 KB 是位宽转换器入口那一级能吃下的**瞬时**突发。报数时不要混用。

## 4. 单块突发会不会溢出

会。最大块的数字：

| 项 | 值 |
|---|---|
| 最大块 | 52,840 B（线上 53,524 B，36 帧） |
| 按 PC 最快 279 Mbit/s 发完 | 1,534 µs = 2.6 × 580 µs 周期 |
| 按网线 1 Gbps 发完 | 428 µs（< 540 µs，理论上塞得进一个周期） |
| 最小块 | 4,702 B（线上 4,778 B）；持续段是 9,256 B |

两层结论：

1. **本机根本发不出「一个周期内塞完最大块」的突发** —— PC 的 `pcap_sendpacket` 上限 279 Mbit/s
   （20,639 帧 / 894 ms，约 43 µs/帧），最大块要 1.53 ms。这类块必然跨周期，
   `blocks_late` 计数就是它们：200/580 µs 下 665 块（27.7%）。
2. **即便如此，块内突发仍然打穿缓冲** —— §3 已证。所以块内限速不是可选项，是必需项。
   若将来把 PC 侧发送提到线速，块内限速的必要性只会更强（4.7 KB → 15.4 KB 峰值积压）。

## 5. 距 64 Gbit/s 架构极限还差多少，差在哪

解码器单实例的实效极限是 **62.2 Gbit/s**（65,536 字 ÷ 540 µs；标称 64 Gbit/s 对应 524 µs 硬底）。
实测 48.3 Gbit/s。逐项归因（全部折成 2403 块的时间）：

| 段 | 时间 s | 解码后 Gbit/s | 说明 |
|---|---|---|---|
| 理想：解码器满载 | 1.298 | 62.1 | 2403 × 540 µs |
| + PC 发送上限 279 Mbit/s | 1.329 | 60.7 | 139 个大块发不完一个周期 |
| + 块内必须限到 200 Mbit/s | 1.502 | 53.7 | 保护接收侧 3.5–4.5 KB 突发容限；模型值 |
| + 调度抖动（`pace_slips=296`） | 1.563 | 51.6 | 实测 `send_ms` |
| + 末帧后 FPGA 收尾 `fpga_wait` | 1.668 | 48.3 | 实测 FPGA 通路 |

**差的 22% 里没有一份是解码器的**：一半是 PC 发送能力（43 µs/帧的 `pcap_sendpacket` 开销，
每帧一次 `std::vector` 分配），另一半是接收侧只有几 KB 突发缓冲逼我们把块内速率砍到 200 Mbit/s。
两条都不需要动解码器就能改：加大 RX 侧突发缓冲、以及把发送端改成零拷贝/批量提交。

## 6. 最优块周期下的全量验收

`--block-period-us 580 --target-mbps 200`，量产无 ILA 位流：

| 项 | 结果 |
|---|---|
| 逐文件（2403 个，各自整块 PC CRC 比对） | **2403 / 2403 通过**，每个 7/7 校验点；命令墙钟 366.6 s |
| 整体单 strip（2403 块一条） | **逐位吻合**：`words=157,450,624`，FPGA `crc32=0xeb3f04cb` = PC 参考，7/7 校验点 |
| 丢帧 | **0**（逐位吻合本身即是证明：任何 STREAM_DATA 丢帧都会改变 CRC 与字数） |

单 strip 的时间分解：

| 段 | 毫秒 |
|---|---|
| 读盘 + 组帧 `prepare` | 107 |
| 发送 `send`（含 START/END） | 1,563 |
| 末帧后 FPGA 收尾 `fpga_wait` | 105 |
| **FPGA 通路合计** | **1,668** |
| PC 参考解码（对答案用，不属于 FPGA 通路） | 21,432 |
| 命令墙钟 | **23,234** |

**2403 块真实墙钟：FPGA 通路 1.668 s**（对应解码后 48.3 Gbit/s）；
整条 verify 命令 23.234 s，其中 21.4 s 是 PC 自己解码一遍做黄金对照，与板卡性能无关。

逐文件那一遍的 366.6 s 里，`fpga_path_ms` 累计 297.7 s —— 平均每文件 124 ms，
而单块解码只要 0.54 ms。这 124 ms 几乎全是每条命令的固定开销（`reset`、STREAM_START
握手、`fpga_wait` 轮询 102 ms）。**逐文件模式不能用来衡量吞吐**，它衡量的是命令开销。

## 7. 并行化 K 与缓冲的换算（只算不做）

### 7.1 核对用户的算法

| 口径 | 到齐时间 @1 Gbps | K = 540 µs ÷ 到齐时间 | 取整 |
|---|---|---|---|
| 最小块 9,256 B（线上 9,389 B） | 75.1 µs | 7.19 | **K = 8** |
| 平均块 12,854 B（线上 13,028 B） | 104.2 µs | 5.18 | **K = 6** |

**算法成立**，结论 K=8 / K=6 也成立（用线上字节比用净荷更严，结论不变）。
唯一要补的是：数据集的绝对最小块是 **4,702 B** 而不是 9,256 B，
但它是孤立的一块，缓冲吃得下，所以按持续段的 9,256 B 定 K 是对的。

### 7.2 K=6 需要多大缓冲

按「每 540/K µs 排空一块、线上以 1 Gbps 连续到达」做逐块最大回撤
（`peak = max Σ(每槽到达字节 − 该块线上字节)`）：

| K | 排空槽 | 每槽到达 | 峰值积压 | 折合 RAMB36 |
|---|---|---|---|---|
| 5 | 108 µs | 13,500 B | 2,227 KB | 495（不可行） |
| **6** | **90 µs** | **11,250 B** | **566 KB** | **129 / 600 = 21.5%** |
| 7 | 77.1 µs | 9,643 B | 76.8 KB | 18 / 600 = 3.0% |
| 8 | 67.5 µs | 8,438 B | 3.6 KB | ~1（等于不用加） |

积压的累积窗口正是那段连续最小块：K=6 时从第 **1834** 块累到第 **2151** 块（318 块）峰值，
K=7 时 1841→2150（310 块）—— 与 E4 定位的 1842–2150 段吻合。

**换算核对结论**：K=8 → K=6 要付 **566 KB**（约 129 个 RAMB36，占 KU040 的 21.5%；
当前整设计才用 18.5 个 tile）。这笔买卖划不划算取决于一个解码实例的 BRAM 成本 ——
若一个实例用不到 65 个 RAMB36，直接上 K=8 更省。

**真正划算的是 K=7**：只要 **76.8 KB**（18 个 RAMB36，3%）就能扛住同一段，
比 K=8 少一个实例、比 K=6 少 489 KB 缓冲。**用户给的两个选项里漏掉了这个点。**

上述都假设 PC/上游能真的打满 1 Gbps；本机现在只能发到 279 Mbit/s，
所以并行化之前得先解决发送端，否则 K 再大也看不出来。

## 8. 复现

```powershell
# 单点
rle4k_v8.exe --iface "\Device\NPF_{...}" --local-mac "EE:EE:EE:EE:B6:4A" `
    send folder "D:\outputs\rle4k_1" --block-period-us 580 --target-mbps 200 --progress-send-pct 0

# 扫描 + 读 VIO（脚本在 .temp/，用完即弃）
#   -tclargs <data> <runs> <cap_mbps|0> <spread|0> <period_us...>
vivado.bat -mode batch -nolog -nojournal -notrace -source .temp\e7_sweep.tcl `
    -tclargs "D:/outputs/rle4k_1" 3 200 0 560 580 600
```

沿用 E4 的两条纪律（扫描用 `send` 不用 `verify`；每档先 `reset` 并核对 `d_mac ≈ 发送帧数`，
否则打 `WINDOW_DIRTY`）。本轮又踩到一次 `WINDOW_DIRTY`：`d_mac` 恰好翻倍到 41,286，
标记按预期挡住了，重跑即恢复。

## 9. 被否掉的一个设计：按块均摊速率

先实现的是 `--block-spread f`：把每块的字节均摊到 `f × 块周期` 上，直觉是「到达速率贴着
解码速率走，积压最小」。**实测基本没用**：600 µs 下 58/57/62 帧，与不限速的 28/60/50 同量级。

原因是均摊对大块无效 —— 52,840 B 摊到 522 µs 需要 838 Mbit/s，远超 PC 的 279 Mbit/s，
节流器一直处于「落后就放弃追赶」状态，等价于不限速。而丢帧恰恰主要由大块的突发造成。
一个**绝对上限**才管用。`--block-spread` 保留在 CLI 里（默认 0 = 关），但不要拿它当主用手段。

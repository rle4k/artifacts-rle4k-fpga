# S5 / S6 / S7 板级结果（2026-08-08）

固件：`fw=0x80104` + RGMII TX `DELAY_VALUE=250`（见 `2026-08-08-rgmii-delay-sweep.md`）。
样本：`D:\outputs\rle4k_sim_strip`（2 块）、`D:\outputs\rle4k_1`（2403 块，单条带）。

---

## 1. +7 字：不是以太网最小帧填充

用户假设为 802.3 最小帧补零。**已用线上抓包与 RTL 双向否定。**

### 1.1 线上实测（tshark，`eth.dst==00:0a:35:00:01:02`）

| 帧 | 线上长度 | cmd | 声明 len | 说明 |
|---|---|---|---|---|
| 2 | 60 | `0x40` STREAM_START | 24 | 43 B → **确被填充到 60**，但按声明长度解析，填充不入数据路径 |
| 3–11 | 1511 | `0x41` STREAM_DATA | 1492 | `14 + 5 + 1492 = 1511`，无填充 |
| 12 | 471 | `0x41` STREAM_DATA | 452 | `14 + 5 + 452 = 471` ≫ 60，**无填充** |
| 13 | 60 | `0x42` STREAM_END | 0 | 被填充，但无载荷 |

最短的 STREAM_DATA 帧是 471 B，远超 60 B 门限，**没有任何数据帧被填充**。

### 1.2 RX 路径按协议头长度截断，不按帧边界

`rle4k_stream_adapter_v8.v:441` 明确以协议头 `len` 字段划定喂给解码器的范围：

```verilog
feed_byte_idx <= 16'd5;                  // 跳过 PayloadHeader
feed_end_byte <= 16'd5 + get_u16(3);     // 5 + 声明 len，与帧长无关
```

即使帧被填充，填充字节也不会进入解码器。**帧填充假设在两个独立层面均被排除。**

### 1.3 协议自身的 4 字节对齐尾填充也已排除

`StreamStartPayload` 会补 0–3 个 `0x00` 使线上长度 4 对齐，`rle4k_decoder_core.v:68`
用 `in_rle_payload = (stream_byte_idx < cfg_rle_payload_bytes)` 把尾填充挡在码流解析器之外。

决定性证据：`--max-blocks 4..12` 全部 `rle_payload == wire_bytes`（**pad = 0**），
其中仍有 4/5/9/10/11 出现 +7。**尾填充无关。**

### 1.4 真实性质：非确定性竞争，量子恒为 +7 字

同一命令重复执行，结果在 0 与 +7 之间跳变（`--inter-chunk-delay-ms 1`）：

| blocks | rle=wire (pad=0) | delta 重复 3 次 |
|---|---|---|
| 4 | 36864 | 7, 0, 7 |
| 5 | 46080 | 7, 7, 7 |
| 6 | 55296 | 0, 0, 0 |
| 7 | 64512 | 0, 0, 0 |
| 8 | 73728 | 0, 0, 0 |
| 9 | 82944 | 7, 7, 0 |
| 10 | 92160 | 7, 0, 7 |
| 11 | 101376 | 7, 0, 0 |
| 12 | 110592 | 0, 0, 0 |

特征：**永远恰好 +7 字（7 × 512 bit = 3584 bit），从不出现 1–6 或 8**；
CRC 随之改变且逐次不同；`crc` 重复查询 5 次读数完全稳定（`0xc3058679` ×5），
故**不是读回通路问题，是解码确实多产出 7 个字**。
`reset`（软复位）前置无效（仍 7/0 混合），故**不是上一轮残留状态**。

### 1.5 已定位的物理层嫌疑：RGMII RX 保持时间违例

当前布线后时序：`WNS=+0.350`（建立满足），`WHS=-0.757`，**违例端点恰好 5 个**，
全部是 RGMII 接收数据脚进 ISERDESE3：

```
Source: PHYA_rgmii_rxd[3]  →  rgmii_interface/rxdata_in_bus[3].rgmii_rx_data_in/D
Path Type: Hold (Min at Slow Process Corner)   Slack -0.757 ns
```

这正是已修复的 TX 延时问题的**镜像**：PHY 自带 RX 延时，而 RXC 是 `IBUF → BUFG` 直连无 IDELAY，
数据相对时钟到得过早。`-0.757 ns < IDELAY 上限 1250 ps`，**数据侧加延时在理论上可补偿**（TX 侧同法已验证有效）。

> 未完成：RX 数据侧 IDELAY 扫描。这是 +7 的首要待验证根因，方法与 TX 扫描完全一致
> （routed checkpoint 改 `DELAY_VALUE` 重生成 bit，约 6 min/档）。

## 2. S5 端到端黄金对照：**通过**

`verify folder D:\outputs\rle4k_sim_strip --fpga-only --inter-chunk-delay-ms 1`（及 `2`）：

| 项 | 黄金值（`pc_reference`） | FPGA 实测 | 结论 |
|---|---|---|---|
| word_count | 98688 | **98688** | 一致 |
| CRC32（post-XOR） | `0xf87c04d1` | **`0xf87c04d1`** | 一致 |

1 ms 与 2 ms 各 3 次，6/6 逐位一致。

**逐块口径说明（诚实边界）**：硬件只暴露 5 个诊断检查点（word 0/128/255/256/32768，
`DecodeCrcPayload.diag_crc[5]`），**不提供逐块 CRC**。逐块一致性由仿真侧覆盖：
`tb/sim_data/ref_crc.txt` 的 `BLOCK0_CRC_ACCUM=0x3e1e302d`、`BLOCK1_CRC_ACCUM=0x0783fb2e`
在 `tb_rle4k_integration` / `tb_rle4k_fullspeed` 中逐块吻合。
故：**条带级板上逐位一致 + 块级仿真逐块一致**，板上逐块 CRC 需新增 RTL 才能给出。

## 3. S6 全速吞吐：**未通过，瓶颈已量化定位**

### 3.1 文档更正

`--inter-chunk-delay-ms` **默认就是 0（全速）**。历史文档中"存在 1 ms 帧间延时需要去掉"的说法**作废**，
不要再引用。`--full-speed` 只是显式覆盖 JSON 配置，与默认值等价。

### 3.2 实测吞吐

| 配置 | 帧数 | 载荷 | 用时 | 载荷吞吐 | 线速 | 结果 |
|---|---|---|---|---|---|---|
| 全量 0 ms | 20639 | 30.79 MB | 912.6 ms | **32.18 MB/s** | **273.4 Mbps** | 解码失败（`words=0`） |
| 全量 1 ms | 20639 | 30.79 MB | ~20.6 s | 1.49 MB/s | 12.7 Mbps | **逐位通过** |
| 小样 0 ms | 10 | 13.88 KB | 0.69 ms | 19.06 MB/s | 162.1 Mbps | +7 |
| 小样 1 ms | 10 | 13.88 KB | 17.6 ms | 0.75 MB/s | 6.4 Mbps | 通过 |

发送侧折算源数据率：`compressed_Mbps=224.7`，`source_Mbps=73535`。

### 3.3 零丢帧？**否。全速丢 17%。**

VIO 计数器在一次全速全量 `send` 前后对照（`send` 不等解码，纯测 RX 通路）：

| 探针 | 前 | 后 | 增量 |
|---|---|---|---|
| `dbg_rx_mac_frames` | `0x5e7d`=24189 | `0xaf56`=44886 | **20697** |
| `dbg_rx_dwc_frames` | `0x5139`=20793 | `0x9455`=37973 | **17180** |
| `dbg_proto_rx_frames` | `0x5140`=20800 | `0x9460`=37984 | **17184** |
| `dbg_rx_mac_err` | `0x0000` | `0x0000` | **0** |

TEMAC 收下 20697 帧（≈ 主机发的 20639 + 少量控制帧），只有 17180 帧穿过位宽转换/包 FIFO：
**丢 3515 帧（17.0%），且 FCS 错误为 0** —— 纯粹是缓冲溢出，不是物理层误码。

对比：1 ms 节流下三个计数器逐帧相等（早前一次 10 帧突发测得 `mac = dwc = proto = 297`），零丢帧。

### 3.4 瓶颈在哪一段：`rle4k_mac_proto_v8` 的存储转发 RX

`mac_proto` 工作在 `clk_15_625` × 64 bit = **恰好 1 Gbps**，且 RX 是**串行的存储转发**：

```
RXS_CAPTURE (N 拍) → RXS_CHECK (1 拍) → RXS_REPLAY (N-1 拍)
```

1511 B 帧 = 189 个 64 bit 字：捕获 189 + 校验 1 + 回放 188 = **378 拍**，
而线上每 189 拍就到一帧。**结构上只能吃约 50% 线速**，且回放期间 `mac_rx_ready` 拉低。
`rx_packet_fifo0` 只能吸收突发，持续背靠背必然溢出 —— 与 17% 丢帧完全吻合。

**要达成全速必须改架构**（三选一，均需先过 TB）：
1. `mac_proto` RX 改**直通（cut-through）**，捕获与回放重叠；
2. 加深 `rx_packet_fifo0` 至能吸收整条带的赤字（本例需 ~15 KB/10 帧，全量不可行）；
3. 提高协议域时钟或位宽（如 64 bit @ 31.25 MHz），给回放留出余量。

现有 TB 复现不了此缺陷：`tb_rle4k_chain` 直接驱动 `mac_proto`，
**绕过了 TEMAC / `rx_packet_fifo0` / `axis_dwidth_converter`**，
所以 `gap=0` 的 `tb_rle4k_fullspeed` 恒过。补此类缺陷需要 master_wrapper 级 TB。

## 4. S7 全量验收

`D:\outputs\rle4k_1` 是**单条带 2403 块**（不是 2403 个独立样本），
压缩载荷 30,792,855 B，`total_height=1230083`，期望 157,450,624 字。

**最好结果（1 ms 节流，一次全量）**：

```
fpga_words = 157450624 = expected_words   delta = 0
```

即**整个 30.8 MB 数据集一次性逐位解码正确**。

### 通过率与失败归因

板级共 71 次 verify（1 ms 节流，块数 2..2403 各档），**35 次 delta=0，通过率 49.3%**。
失败**全部**是同一类：

| 归因类别 | 次数 | 占比 | 特征 |
|---|---|---|---|
| A：+7 字竞争（疑 RGMII RX 保持违例） | 36 | 50.7% | 恒 +7 字，CRC 随之变化，与块数/节流/软复位无关 |
| B：数据内容错误 | 0 | 0 | 未观察到 |
| C：丢帧/超时 | 0 | 0 | 1 ms 节流下计数器逐帧相等 |

按块数看并非均匀随机：6/7/8/12 块 12 次全过，5 块 7 次全 +7，4/9/10/11 块混合。
说明该竞争对**特定长度/边界**敏感，叠加时序余量不足 —— 与 RX 保持违例的表现一致。

全速（0 ms）下另有 D 类失败：RX 缓冲溢出丢 17% 帧，解码无法完成（`words=0`）。

## 5. 结论

| 项 | 状态 |
|---|---|
| +7 根因 | **不是帧填充**（已实测否定）；是非确定性竞争，首要嫌疑 RGMII RX 保持违例 `-0.757 ns` |
| S5 黄金对照 | **通过**（条带级逐位一致；逐块一致性由仿真覆盖） |
| S6 全速 | **未通过**：全速丢 17% 帧；瓶颈 = `mac_proto` 存储转发 RX 只能吃 50% 线速 |
| S7 全量 | 全量一次性逐位正确；但受 A 类竞争影响，通过率 49.3% |

### 待办（按优先级）

1. **RX 数据侧 IDELAY 扫描**（同 TX 手法，6 min/档），目标 `WHS ≥ 0`，验证 +7 消失。
2. `mac_proto` RX 改直通 + master_wrapper 级 TB，解 S6。
3. 板级逐块 CRC 需新增 RTL（当前只有 5 个固定检查点）。

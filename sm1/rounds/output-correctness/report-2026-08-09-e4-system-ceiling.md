# E4 —— 实测真实系统天花板

数据：`D:\outputs\rle4k_1`（2403 块，压缩 30,792,856 B，解码后 157,450,624 字 = 80.615 Gbit）。
位流：`reports/bitstreams/2026-08-09-streamend-drainfix-PROD-noila`（量产、无 ILA、`DELAY_VALUE=250`）。
判据：VIO 的 `dbg_rx_mac_frames` 与 `dbg_rx_dwc_frames` 之差，即在 8→64 位宽转换器入口被丢掉的帧。

## 1. 结论

**整机稳定吞吐上限 = 压缩侧 136.7 Mbit/s**（线上字节口径，含以太网头与最小帧填充，不含前导与 IFG）。

拐点很锐：136.5 Mbit/s 连跑 5 次零丢帧，137.9 Mbit/s 就有 3/5 次丢 2–4 帧。
再往上丢帧率单调上升，到 167.6 Mbit/s 已丢约 300 帧（1.5%）。

V1023 §2 预测 182 Mbit/s。**实测低 25%，模型的机理对、统计口径错**，见 §3。

## 3. 与模型的差异：错在用平均膨胀比

V1023 §2.2 的公式是

```text
压缩侧上限 = 64000 Mbit/s / 膨胀比,   膨胀比 = 解码后字节 / 压缩字节
```

代入 `rle4k_1` 的**全集平均** 327.25×，再乘 92.8% 效率，得 182 Mbit/s。

机理没问题（瓶颈确在解码器输出口，且丢弃点的位置也印证了背压来自下游）。
错的是**把平均值当成了约束**。

**每块解码后恒为 4 MiB，与压缩后大小无关，所以每块的解码耗时是常数**（实测约 540 µs）。
于是压缩侧可持续速率由**最小的块**、也就是**最大的膨胀比**决定，不是平均值。
缓冲只能吃掉短暂的赤字，吃不掉持续的。

`rle4k_1` 的最小块是 9256 B，而且**不是孤例**：第 1842–2150 块是一段 **309 块的连续最小块**
（另有 657–729 的 73 块一段，以及开头 15 块）。

```text
9256 B / 540 µs = 17.14 MB/s = 137 Mbit/s
```

与实测 136.7 Mbit/s 吻合到 0.3%。

### 3.1 用三个子集把它证死

从同一数据集里挑出膨胀比不同的 200 块子集，各自扫拐点。若模型该用平均值，
拐点应随子集平均膨胀比变化；若该用最小块，均匀子集才会与公式相符。

| 子集 | 平均块长 | 膨胀比 | 公式（×92.8%） | 实测拐点 |
|---|---|---|---|---|
| 最小 200 块（块长几乎全等） | 9,233 B | 454.3× | 130.7 | **≈137**（135 干净 / 140 丢） |
| 数据集前 200 块（前 15 块最小，随后变大） | 14,952 B | 281.2× | 211 | **≈157**（155 干净 / 160 丢） |
| 最大 200 块 | 23,851 B | 175.9× | 337.6 | **≥218**（PC 发不上去，仅得下界） |
| 全量 2403 块 | 12,814 B | 327.3× | 182 | **136.7** |

读法：

- **最小 200 块**块长几乎全等，局部 = 平均，公式因此对得上（130.7 vs 137，差 5%）。
- **前 200 块**只有开头 15 块是最小块，缓冲能吃下这 15 块的赤字，所以拐点(157)高于按最小块算的
  137、又远低于按平均算的 211 —— 正好落在两者之间，这就是"局部约束 + 有限缓冲"的指纹。
- **全量**有 309 块的连续最小块，缓冲吃不下，于是拐点被压到最小块决定的 137。

### 3.2 顺带修正效率取值

V1023 用的 92.8% 来自 `sim_strip` 单样本。用本次拐点反推：
最小块 9256 B 在 136.5 Mbit/s 时用 541.8 µs 送完（干净），在 137.9 Mbit/s 时 537.6 µs（丢帧），
故每块解码耗时落在 537.6–541.8 µs，取 540 µs。

```text
540 µs × 125 MHz = 67,500 周期 / 65,536 字 = 97.1% 效率
```

即解码器实效 **62.2 Gbit/s**（解码后），而非 59.4。**效率被低估了，天花板被高估了** ——
两个错误方向相反，所以 182 这个数字看起来"差不多"，其实两处都不准。

### 3.3 有效缓冲约 20 KB，不是标称 34 KB

用 309 块那段反推：在 137.9 Mbit/s 时每块赤字 `540 − 537.6 = 2.4 µs`，
折合 `2.4 µs × 17.24 MB/s ≈ 41 B/块`，309 块累计约 12.7 KB 才开始丢；
前 200 块那组在 160 Mbit/s 时 15 块累计约 23 KB 丢。两者夹出的有效缓冲在 **13–23 KB**，
低于第 4/5/10 级标称合计的 34 KB。差额是各级的水位阈值与 `almost_full` 余量，符合预期。

## 4. 天花板速率下的全量验收

`--target-mbps 138`（达成 136.0 Mbit/s），量产无 ILA 位流：

| 项 | 结果 |
|---|---|
| 逐文件（2403 个，各自整块 PC CRC 比对） | **2403 / 2403 通过**，每个 7/7 校验点吻合；耗时 368.7 s |
| 整体单 strip（2403 块一条） | **逐位吻合**：`words=157,450,624`，FPGA `crc32=0xeb3f04cb` = PC 参考，7/7 校验点 |
| 丢帧 | **0** |

单 strip 那次的时间分解：

| 段 | 毫秒 |
|---|---|
| 读盘 + 组帧 `prepare` | 109 |
| 发送 `send`（含 START/END） | 1,854 |
| 末帧后 FPGA 收尾 `fpga_wait` | 106 |
| **FPGA 通路合计** | **1,960** |
| PC 参考解码（仅为对答案，不属于 FPGA 通路） | 15,916 |
| 命令墙钟 | **18,008** |

所以"2403 块总时间"有两个诚实的口径：

- **FPGA 端到端 1.960 s** —— 这是板卡实际吃完 10.08 GB 解码后数据的时间，对应解码后吞吐 **41.1 Gbit/s**；
- **整条 verify 命令 18.008 s** —— 其中 15.9 s 是 PC 自己解码一遍来做黄金对照，与 FPGA 性能无关。

## 5. 过程中被修掉的一个测量陷阱：节流器不能追赶

第一版节流器用**累计截止时间**（`sent_bits / rate` 对总耗时），这在纸面上正确，
但 Windows 一旦把发送线程调走几毫秒，节流器随后就会**以线速猛发**把欠的时间补回来。
这种突发会打穿接收侧那 20 KB 缓冲，于是**每个速率档都出现约 0.1% 的随机丢帧底噪**：

```text
120 Mbit/s 三次：丢 23 / 32 / 0 帧     ← 平均速率远低于天花板，却在丢帧
```

看起来完全像 V1023 附录 A.5 说的"存在第二个与速率无关的丢帧源"，实际是测量工具自己造的。

改成**放弃追赶**（落后超过一帧时把时间原点前移，只保留一帧的突发容差）之后，
120 与 135 档变成 3/3 全零，拐点也从模糊变得锐利。代价是达成速率比设定值低 1–1.5%，
所以表里必须报**达成值**而不是设定值。

`pace_slips` 计数已并入 `THROUGHPUT` 行：全量那次 20,639 帧里 128 次放弃追赶（0.6%）。

## 6. 复现方法

```powershell
# 单点：
rle4k_v8.exe --iface "\Device\NPF_{...}" --local-mac "EE:EE:EE:EE:B6:4A" `
    send folder "D:\outputs\rle4k_1" --target-mbps 138 --progress-send-pct 0

# 扫描 + 读 VIO（脚本在 .temp/，用完即弃）：
vivado.bat -mode batch -nolog -nojournal -notrace -source .temp\e4_sweep.tcl `
    -tclargs "D:/outputs/rle4k_1" 3000 5 136 137 138 139
```

两个坑，踩过：

1. **扫描要用 `send` 不能用 `verify`**。丢帧时如果 `STREAM_END` 也在丢的那批里，
   解码器永远不报 done，`verify` 会轮询几分钟，而**每次轮询都是一帧 RX**，
   直接落进我们正在测量的采样窗口里，把丢帧率算成负数或几倍。
2. **每档之前先 `reset`，并核对 `d_mac ≈ 发送帧数`**。上一轮残留的 CLI 进程或没排空的解码器
   会把上一档的流量算进这一档，表现为 `d_mac` 恰好翻倍。脚本里有 `WINDOW_DIRTY` 标记专门挡这个。
